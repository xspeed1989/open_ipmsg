# ADR-0006：钥匙新鲜度要结构化判断，文本只当兜底

- 状态：**已落地**（检查 3；检查 1 原已存在；检查 2 由检查 3 覆盖）
- 相关：ADR-0005

## 背景

ADR-0005 让「出站失败」能自愈，但它依赖对端回的那句文本。而这个判据在**协议层是唯一**的：
原版 IPMsg 的解密失败回执就是一条普通 `IPMSG_SENDMSG`。真正的问题是「我方缓存的钥匙是否还新」
**没有可验证的判据**，只能等出错。

## 落地情况

1. **入站验签失败即视为轮换 —— 原已存在**：EncIPDict 的候选公钥循环全部不命中时，
   会走 `crypto_rehandshake(ctx, from, key, "encipdict-key-mismatch")`（`GETPUBKEY` + 主动推
   `ANSPUBKEY`，由 `try_rehandshake_gate` 按 10s/IP 限频）。这条与 ADR-0005 对称，**不必重写**。
2. **发送前校验指纹 —— 由第 3 条覆盖**：发送路径没有单一收口（多处 `peer_pubkey()` 取钥匙），
   而周期确认的扫描间隔是 2s（`HANDSHAKE_RETRY_INTERVAL_SECS`）—— 阈值一到，最多 2s 内就会
   补一次确认，效果等价于「发送前后校验」，却不必在每个发送点插桩。**尤其是进程刚起来、
   缓存来自磁盘的那一刻**（`peer_key_age_secs() == None`）算作「从未确认」→ 立刻确认，
   正是 ADR-0005 那个「原版重启过、我们拿着旧钥匙」的场景。
3. **周期性确认 —— 已落地**：`net.rs` 的 `refresh_stale_peer_keys` 挂在 `handshake_sweep` 的
   第二遍上：对**已缓存公钥**、声明加密、未被标成明文的对端，钥匙「太久没确认」（默认 300s）
   或「从未确认」时补发一条 `GETPUBKEY` 重新确认。
   - 用的是**不计入探测预算**的发送（`send_getpubkey_maintain`，与 `send_getpubkey_retry` 同一条
     原则）：那条预算判「对端能力」，攒够会把对端标成明文，不该由「我方缓存是否新鲜」决定；
   - **独立的限频**（`try_key_refresh_gate`，60s/IP），与 `probe_counts`、`handshake_retries`
     三者分开计数，互不干扰；
   - 判据抽成 `key_needs_refresh(age)` 单独可测（None/到阈值 → 该确认；刚确认过 → 不动）。
4. 文本判据（ADR-0005）**保留为兜底**，仍不作为主手段。

## 后果

- 「对端换了钥匙、而它的上线宣告在 LAN 上丢了」这类故障（ADR-0005 的前置条件）现在会在
  **≤300s + 2s** 内自己发现并修好，不再依赖对端抱怨。
- 代价：每对端 5 分钟一个 UDP 小包（对端回一条 `ANSPUBKEY`，顺手把新鲜度刷新）。
